# Error Analysis

`package_01` 39페이지 실행(rule-only) 기준 실측 요약: 실제 오분류 1건(p8),
LLM 위임 대상 2건(p8, p36), 논리 재조립 orphan 9건. 실제로 확인된 사례만
기록한다.

## 페이지 단위 사례

### Page 8 — 정답 TITLE_REPORT

**예측:** OTHER

**실행 모드:** rule-only

**원인:** 페이지 전체 텍스트가 다음 두 줄뿐이다(정규화 길이 68자, `package_01`
전체에서 가장 짧음).

```
[ Plat map removed in anonymized sample ]
[ Plat map removed in anonymized sample ]
```

지적도 이미지가 익명화 과정에서 제거되고 대체 텍스트만 남아, `TITLE_REPORT`
시그니처와 페이지 마커가 모두 없다(`matched_class_count=0`, `rule_score=0.00`).

**Fallback 동작:** `SHORT_TEXT`, `LOW_RULE_SCORE` 사유로 LLM 위임 대상에
포함됐다(`run_report.json`의 `llm_target_pages: [8, 36]`). 그러나 실제 LLM
호출부가 미구현이고 API 키도 없어 호출 자체가 발생하지 않았고, 룰의 `OTHER`
예측이 최종 라벨로 남았다.

**개선 방향:** 재조립 문맥(이 페이지가 `CLTA` 마커 기준 8번째 장 다음이라는
사실)을 활용한 문맥 기반 추론. 다만 텍스트 자체에는 판정 근거가 없어 텍스트
전용 LLM으로도 해결이 어렵다.

**남은 위험:** 이 페이지는 현재 접근법(룰 + 텍스트 LLM)으로 구조적으로 해결
불가하다. 시그니처도 마커도 없는 페이지를 `OTHER`로 분류하는 것 자체는
오히려 합리적인 결과일 수 있다는 점을 정직하게 남겨둔다.

### Page 36 — 정답 INCOME_DOC (오분류가 아니다)

**예측:** INCOME_DOC

**실행 모드:** rule-only

**원인:** 손익계산서(Profit & Loss Statement)이지만 제목이 이미지로
렌더링되어 텍스트 레이어에 없다. Paystub, W-2, Form 1040, 1099 등 표준 소득
서류 키워드가 전혀 없고, 매칭된 신호는 weak 시그니처 `CTEC`(가중치 0.25)
하나뿐이다. `rule_score = 0.25 < 0.60`(임계값)이라 `LOW_RULE_SCORE`로
분류된다. 스캔 이미지 5개를 포함한다.

**Fallback 동작:** `LOW_RULE_SCORE` 사유로 LLM 위임 대상에 포함됐다. 실제
호출은 발생하지 않았지만, 룰이 낸 예측(`INCOME_DOC`)이 이미 정답과 일치해
최종 라벨도 정답으로 유지된다.

**개선 방향:** 실제 LLM 호출부 구현 후 재검증이 필요하다 — 현재는 "우연히
맞은 라벨"이라 이 결과만으로 신뢰할 수 없다.

**남은 위험:** **이 사례는 오답이 아니다.** 룰이 낸 라벨이 정답과 일치하지만
근거(`rule_score=0.25`)가 임계값(0.60)에 크게 못 미쳐 신뢰할 수 없는
상태였다. "라벨은 맞을 수 있어도 근거가 약해 추가 검증이 필요한 페이지가
실제로 존재한다"는 사실 — 바로 이 지점이 룰 단독이 아니라 하이브리드(룰 +
LLM) 구조를 채택한 핵심 근거다.

### CREDIT_REPORT 부속 페이지 7장 — orphan (분류는 성공, 재조립은 실패)

**예측:** 7장 전부 `CREDIT_REPORT`로 정확히 예측됨 (p13, p17, p21, p23, p25,
p29 등)

**실행 모드:** rule-only

**원인:** `Credit Score Disclosure`, `Your Credit Score and the Price You
Pay for Credit`, `XACTUS` 등 강한 시그니처로 `CREDIT_REPORT`로 정확히
분류됐다. 그러나 이 페이지들에는 페이지 마커가 없다(`marker_style=NONE`).

**Fallback 동작:** 논리 재조립 tier 3(증거 부족)에 해당해 `is_orphan=True`,
`WarningCode.ORPHAN_PAGE`가 붙는다. 어떤 `ReconstructedDocument`에도 강제로
붙이지 않는다.

**개선 방향:** 서브문서 단위의 별도 마커(예: 각 레터 자체의 페이지 번호)를
새 시그니처로 추가하거나, 좌표 기반 근접성 추출로 식별자를 보강해 tier 1/2로
승격.

**남은 위험:** 분류는 정확하지만 재조립이 실패한 사례다. 실무적으로는
신용보고서 패키지의 일부이지만, 현재 증거(마커 없음, 식별자 없음)로는 붙일
근거가 없다. 이 사례가 물리적 그룹핑(필수)과 논리 재조립(확장)을 분리해 둔
이유이기도 하다 — 분류가 맞았다고 재조립까지 저절로 맞는 것은 아니다.

## 개발 중 발견한 조용한 실패 사례

아래 두 건은 페이지 오분류가 아니라 코드 자체의 결함이다. 둘 다 예외를
발생시키지 않고 결과만 조용히 손상시키는 유형이라는 공통점이 있어 별도로
기록한다. 다만 발견 경로는 서로 다르다 — 하나는 테스트 실패로, 다른 하나는
코드 리뷰 지적을 받아 실제 출력을 직접 대조하는 과정에서 발견됐다. 두 건 모두
예외를 던지지 않는 유형이라는 사실 자체가, 자동 검출(테스트 스위트를 그냥
통과시키는 것)만으로는 이런 결함을 잡기에 불충분하다는 것을 보여준다 — 실제로
두 번째 건은 자동 테스트가 아니라 사람의 리뷰로만 잡혔다.

### `_mask_names` 토큰 간격 버그

**증상:** `"Borrower Name: Jane Smith"`처럼 라벨 뒤에 성+이름 2단어가 오는
경우, 라벨 바로 뒤 첫 토큰(`Jane`)만 인식하고 두 번째 토큰(`Smith`)을 찾지
못해 이름 마스킹이 아예 동작하지 않았다.

**원인:** 토큰 간 공백 위치에서 바로 다음 토큰을 `match` 시도하는 구조라,
공백 한 칸을 건너뛰지 못하고 항상 실패했다.

**발견 경로:** 마스킹 검증 테스트("Realtor 보존", "라벨 근처 인명 마스킹")가
실패하며 발견됐다. 예외가 발생하지 않아 코드 실행 자체는 끝까지 진행됐고,
어서션이 기대값과 실제 마스킹 결과를 비교해 불일치를 잡아낸 경우다.

**개선 방향:** 이미 수정 완료 — 토큰 사이 정확히 공백 한 칸을 확인한 뒤 다음
토큰을 매칭하도록 변경했다.

**남은 위험:** 정규식 휴리스틱 자체의 구조적 한계는 여전히 남아 있다. 인식
라벨(Borrower/Applicant/Signature/Name/Trustor/Attn) 근처가 아닌 곳에 있는
이름은 여전히 마스킹되지 않는다.

### `warnings`와 위임 사유 혼재 버그

**증상:** CLI에 표시되는 p8의 "대표 위임 사유"가 `NO_SIGNATURE`로
나왔다.

**원인:** `PageResult.warnings`에는 분류 단계에서 관찰된 사실(`NO_SIGNATURE`)과
위임을 유발한 조건(`SHORT_TEXT` 등)이 함께 담긴다. 초기 구현이 이 리스트의
첫 항목(`warnings[0]`)을 그대로 "위임 사유"로 표시해, 관찰 결과와 위임 조건을
구분하지 않았다.

**발견 경로:** 테스트가 발견한 것이 아니다. 코드 리뷰에서 이 표시 방식에
대한 지적을 받고, 실제 CLI 출력을 직접 대조하는 과정에서 확인됐다. 예외 없이
실행됐고 기존 테스트도 모두 통과하는 상태였다 — 표시된 값이 "왜 위임됐는가"
라는 질문에 대한 답으로 부정확하다는 점은 값 자체를 눈으로 봐야 알 수 있는
문제였다.

**개선 방향:** 이미 수정 완료 — `should_delegate`가 반환하는 `reasons`를
대표 사유로 사용하도록 표시 계층만 변경했다. `warnings`에는 여전히 두 종류가
함께 담기지만, CLI는 `reasons`와 `warnings`를 별도 컬럼으로 표시해 관찰
결과와 위임 조건을 시각적으로 구분한다.

**남은 위험:** 이번 건은 회귀 테스트로 고정했지만, 애초에 기존 테스트
스위트는 이 문제를 잡지 못했었다 — 코드 리뷰라는 사람의 개입이 없었다면
`warnings[0]`가 계속 대표 사유로 표시됐을 것이다. 이 두 개념(분류 단계 관찰과
위임 조건)을 한 리스트(`warnings`)에 같이 담는 설계 자체는 유지되고 있으므로,
향후 이 필드를 사용하는 다른 코드에서 같은 종류의 혼동이 재발할 가능성은
남아 있다.
